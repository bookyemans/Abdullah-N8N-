# المرحلة السادسة — جاهزية التحقق الفعلي من PostgreSQL / Supabase

## ما تم في هذه الحزمة
- تثبيت ترتيب ملفات migrations المرقمة `0001` إلى `0007`.
- إضافة `BEGIN` و`COMMIT` صريحين إلى migration `0007_admin_bootstrap_hardening.sql` حتى تكون جميع الملفات متسقة في التغليف المعاملي.
- إضافة `scripts/validate-supabase-migrations.mjs` لفحص الترقيم المتسلسل، والتغليف المعاملي، ومنع وجود أسرار أو أوامر هدمية شائعة في ملفات migrations.
- ربط الفحص بأمر `npm run check`.

## ما لم يتم (بوضوح)
لم يتم تنفيذ SQL على PostgreSQL، ولم يتم إنشاء مشروع Supabase أو استخدام بيانات اعتماد حقيقية. بيئة التنفيذ الحالية لا تحتوي على `psql` أو `postgres` أو Docker أو Supabase CLI. لذلك لا يصح وصف هذه المرحلة بأنها اختبار تكامل حي أو اعتماد نهائي لـ RLS.

## تشغيل التحقق محلياً عند توفر Docker وSupabase CLI
من مجلد المشروع:

```bash
supabase start
supabase db reset
```

ينبغي أن يعيد `db reset` إنشاء قاعدة محلية فارغة وتطبيق جميع migrations بالتسلسل. بعد ذلك راجع المخطط:

```bash
supabase db lint --local
supabase test db
```

إذا لم يكن `supabase test db` مجهزاً بملفات pgTAP في المشروع، فلا تعتبر عدم وجود الاختبارات نجاحاً؛ أضف اختبارات pgTAP قبل اعتماد RLS.

## اختبار مشروع Supabase بعيد
1. أنشئ مشروعاً تجريبياً منفصلاً عن الإنتاج.
2. اربطه باستخدام `supabase link --project-ref <PROJECT_REF>` من بيئة المطور الآمنة.
3. خذ نسخة احتياطية/تأكد من أن المشروع فارغ، ثم نفّذ `supabase db push`.
4. لا تضع Service Role Key في ملفات المشروع أو أوامر محفوظة في سجل shell؛ استخدم مخزن أسرار آمن.
5. أنشئ مستخدم اختبار عادي، ومديراً، ومالكاً وفق `ADMIN_ACCOUNT_SETUP.md`.
6. اختبر القراءة المسموحة لكل دور، وتأكد من رفض الكتابة المباشرة إلى الجداول الحساسة من `anon` و`authenticated`.
7. اختبر RPC التحليلات بحساب غير إداري وبحساب مدير نشط وبحساب مدير معطل؛ يجب رفض غير الإداري والمعطل.
8. اختبر حذف/تعطيل آخر مالك، وتغيير دور المستخدم لنفسه، والوصول إلى سجلات النشاط؛ يجب رفض كل محاولة غير مصرح بها.

## تنبيه بشأن RLS
بعض عمليات الخادم تستخدم Service Role بعد التحقق من Access Token والدور في Cloudflare Functions. مفتاح Service Role يتجاوز RLS بطبيعته؛ لذلك يجب اختبار التحقق من الدور في Functions أيضاً، لا الاكتفاء باختبار سياسات PostgreSQL.

## متطلبات قبل الاعتماد
- نجاح `supabase db reset` على قاعدة محلية نظيفة.
- نجاح lint SQL دون أخطاء.
- اختبارات pgTAP فعلية لسياسات RLS والدوال الحساسة.
- اختبار Auth ودعوات المستخدمين والبريد في مشروع تجريبي.
- اختبار APIs مع مفاتيح مشروع تجريبي حقيقية مخزنة في Secrets فقط.
