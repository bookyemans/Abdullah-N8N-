# تقرير المرحلة السادسة — تحليلات التحويلات وأداء العملاء المحتملين

## الهدف
ربط بيانات الزيارات بطلبات التواصل في تقرير إداري واحد، حتى يمكن قياس جودة مصادر الزيارات والصفحات والخدمات المطلوبة، وليس الاكتفاء بعدّ مشاهدات الصفحات.

## ما تم تنفيذه

### 1. قاعدة البيانات
أضيف الترحيل:
`supabase/migrations/0005_conversion_analytics.sql`

ويضيف دالة PostgreSQL آمنة باسم `public.admin_conversion_summary(p_days)`، تقوم بالتجميع داخل Supabase وتعيد:
- الزوار الفريدين ومشاهدات الصفحات والجلسات.
- طلبات التواصل غير المصنفة كرسائل مزعجة.
- عدد الزوار المحولين ومعدل تحويل الزوار.
- معدل الطلبات إلى الزوار (قد يتجاوز 100% إذا أرسل الزائر أكثر من طلب).
- الطلبات المفتوحة، التي تم الرد عليها، المغلقة، والمزعجة.
- نقرات واتساب.
- الاتجاه اليومي للزيارات والطلبات.
- أداء مصادر الزيارات، الخدمات المطلوبة، وصفحات المصدر.

تتحقق الدالة من `public.is_active_admin()`، وتُمنع صلاحية `anon` وتُمنح صلاحية التنفيذ لدور `authenticated` فقط. وتبقى واجهة API مسؤولة أيضاً عن التحقق من جلسة المسؤول.

### 2. واجهة API
أضيف:
`GET /api/admin/conversions?days=30`

- يقبل 1 إلى 90 يوماً ويحد أي قيمة أعلى إلى 90.
- يستخدم JWT للمسؤول مع مفتاح anon في استدعاء RPC، فلا يعتمد على تنزيل صفوف الأحداث الخام.
- لا يعيد بيانات الاتصال الشخصية للعملاء.

### 3. لوحة التحويلات
أضيفت الصفحة:
`/admin/conversions.html`

وتعرض:
- بطاقات الزوار والعملاء المحتملين ومعدل التحويل ونقرات واتساب.
- مسار التحويل من الزائر إلى الجلسة والنقر والتواصل.
- رسم مقارنة يومي لمشاهدات الصفحات وطلبات التواصل.
- جدول أداء مصادر الزيارات ومعدلات تحويلها.
- الخدمات الأكثر طلباً.
- الصفحات التي جلبت طلبات تواصل.
- توزيع حالات العملاء المحتملين.

أضيف رابط «التحويلات» إلى قائمة التنقل المشتركة في لوحة الإدارة.

## تعريفات القياس وحدوده
- **معدل تحويل الزوار** = الزوار الذين لديهم طلب تواصل غير مزعج ومربوط بمعرف زائر ÷ الزوار الفريدين المسجلين في أحداث مشاهدة الصفحات × 100.
- **معدل الطلبات إلى الزوار** = عدد طلبات التواصل غير المزعجة ÷ الزوار الفريدين × 100. قد يتجاوز 100% عند تعدد الطلبات من الزائر نفسه.
- الطلبات التي لا تحمل `visitor_id` لا تدخل في عدد الزوار المحولين، لكنها تدخل في إجمالي الطلبات.
- إسناد المصدر يعتمد أولاً على `utm_source` ثم `source` من جلسة الطلب، ثم `referral_source` كقيمة احتياطية. لذلك قد لا يكون للطلبات غير المرتبطة بجلسة معدل مصدر قابل للحساب.
- المصدر قد يتكرر للزائر نفسه عبر جلسات مختلفة؛ تقرير القنوات هو إسناد حسب المصدر المرتبط بالجلسة، وليس نموذج إسناد إعلاني متعدد اللمسات.
- نقرات واتساب ليست بالضرورة طلبات تواصل مكتملة.
- كل الأوقات محفوظة كـ `timestamptz` وتعرضها الواجهة بحسب إعدادات المتصفح.

## الاختبارات المنفذة
- `npm test`: ناجح، بما في ذلك اختبار API الجديد للتحقق من المصادقة، واستدعاء RPC، وتحديد نطاق الأيام، ورفض الجلسة غير الصالحة.
- `npm run check`: ناجح.
- فحص HTML: 40 صفحة، صفر مراجع محلية مفقودة.
- كتالوج المشاريع: 12 سجلاً سليماً.
- كتالوج المقالات: 14 بطاقة، 13 مقالاً مرتبطاً، وبطاقة واحدة غير متاحة كما كانت سابقاً.
- فحص المكونات المشتركة: 12 مكوناً عبر 6 صفحات.

## ما لم يتم اختباره
هذه اختبارات محلية ومحاكاة HTTP وفحوص SQL ساكنة. لم يتم تشغيل الترحيل على مشروع Supabase حقيقي، ولا اختبار PostgreSQL/RLS فعلي، ولا نشر Cloudflare Pages، ولا اختبار متصفح حي.

## خطوات التفعيل
1. خذ نسخة احتياطية من مشروع Supabase قبل الترحيل.
2. نفّذ `0005_conversion_analytics.sql` بعد `0004_lead_management.sql` من Supabase SQL Editor أو عبر Supabase CLI.
3. انشر ملفات المشروع على Cloudflare Pages بعد ربط المستودع.
4. سجّل الدخول بحساب Owner وافتح `/admin/conversions.html`.
5. تحقق من الأرقام بمقارنتها مع سجلات `tracking_events` و`contact_submissions` ضمن الفترة نفسها.

لا يتطلب هذا الترحيل مفتاحاً سرياً جديداً، ولا يعتمد على Google Sheets. Supabase يظل المصدر الأساسي للبيانات.
